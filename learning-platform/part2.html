🌐 LangGraph — State Machines for AI Pipelines

LangGraph is the most architecturally interesting library in your Code Review Agent. It turns your pipeline from a chain of function calls into a formal state machine that can be composed, branched, and extended without touching existing code.

What Problem Does LangGraph Solve?

Without LangGraph, you have ReviewService.run_review() — a linear function that calls steps 1-5 in order. It works, but:

  • Adding a new step requires editing the existing function (breaks Open/Closed principle)
  • Error handling is scattered with try/except in each step
  • You cannot run steps in parallel (e.g., run security scan + LLM review simultaneously)
  • You cannot easily add conditional branches (e.g., if diff > 10,000 chars, use a different prompt)

LangGraph models the pipeline as a directed graph where each node is a pure function. Edges define the flow. The compiled graph is a runnable object you invoke with initial state.

app/agents/review_agent.py — State definition
from __future__ import annotations
import operator
from typing import Annotated, Any, TypedDict
from langgraph.graph import END, StateGraph

# AgentState is a TypedDict — it defines the shape of the shared
# mutable state that ALL nodes read from and write to.
class AgentState(TypedDict):
    repo: str                    # read-only: set at invocation
    pr_number: int               # read-only
    post_comment: bool           # read-only
    pr_diff: PRDiff | None       # written by fetch_diff_node
    raw_llm_response: str        # written by llm_review_node
    parsed_data: dict[str, Any]  # written by parse_response_node
    review: CodeReview | None    # written by build_review_node
    review_id: str               # written by persist_review_node
    error: str                   # written by any node on failure

    # Annotated[list[str], operator.add] is special LangGraph syntax.
    # It means: when a node returns {"logs": ["new entry"]},
    # LangGraph APPENDS to the existing list (reducer = operator.add)
    # instead of REPLACING it. Without this, each node would overwrite
    # the previous logs.
    logs: Annotated[list[str], operator.add]

Nodes — Pure Functions That Return Partial State

Every node receives the full AgentState and returns a partial dict of only the fields it wants to update. LangGraph merges this with the existing state.

The key pattern in your code: every node first checks if state.get("error") and returns {} immediately. This is the short-circuit pattern — once any node fails, all subsequent nodes silently skip.

Graph assembly — wiring nodes + edges + compiling
from langgraph.graph import END, StateGraph

def build_review_graph() -> StateGraph:
    graph = StateGraph(AgentState)   # pass TypedDict class as schema

    # Register each node: (name, async_function)
    graph.add_node("fetch_diff",     fetch_diff_node)
    graph.add_node("llm_review",     llm_review_node)
    graph.add_node("parse_response", parse_response_node)
    graph.add_node("build_review",   build_review_node)
    graph.add_node("persist_review", persist_review_node)
    graph.add_node("post_comment",   post_comment_node)

    # Set entry point (first node to execute)
    graph.set_entry_point("fetch_diff")

    # Linear edges: A always goes to B
    graph.add_edge("fetch_diff",     "llm_review")
    graph.add_edge("llm_review",     "parse_response")
    graph.add_edge("parse_response", "build_review")
    graph.add_edge("build_review",   "persist_review")
    graph.add_edge("persist_review", "post_comment")
    graph.add_edge("post_comment",   END)   # END is special: terminates graph

    return graph.compile()  # returns a CompiledStateGraph (runnable)

Mental Model

Think of LangGraph like a factory assembly line. The conveyor belt (graph) moves a work item (state) through stations (nodes). If a station breaks (error), the item is flagged and all downstream stations just let it pass through without touching it. At any point you can insert a new station into the line or split the line into two parallel tracks.

🤖 Anthropic Claude API — Messages, Caching, Streaming

Claude is the LLM powering your Code Review Agent and Lead Classifier. Understanding the SDK deeply lets you optimize cost, avoid timeouts, and explain every API decision in interviews.

The Messages API — Core Structure

Every Claude API call is a messages.create() call. The structure is:

ParameterTypePurpose
modelstringWhich Claude model: claude-sonnet-4-6, claude-opus-4-7, etc.
max_tokensintMax tokens in the response. Not a limit on your input.
systemstr or listSystem prompt — sets Claude's persona and instructions
messageslist of dictsConversation history: [{"role": "user", "content": "..."}]
app/services/llm/claude_client.py — your actual implementation
import anthropic
from app.config import get_settings

# This is the cached system prompt — the ENTIRE expert persona + JSON schema.
# It never changes between requests, making it perfect for caching.
_SYSTEM_PROMPT = (
    "You are an expert software engineer performing a thorough code review. "
    "You will be given a git diff of a pull request. "
    "Respond ONLY with a single valid JSON object — no prose before or after. "
    # ... the full JSON schema definition ...
)

class ClaudeClient(BaseLLMClient):
    def __init__(self) -> None:
        settings = get_settings()
        # AsyncAnthropic = async client (use with await)
        # Anthropic = sync client (use without await)
        self._client = anthropic.AsyncAnthropic(api_key=settings.anthropic_api_key)
        self._model = settings.claude_model  # "claude-sonnet-4-6"

    async def generate_review(self, prompt: str) -> str:
        message = await self._client.messages.create(
            model=self._model,
            max_tokens=4096,
            system=[
                {
                    "type": "text",
                    "text": _SYSTEM_PROMPT,
                    # THIS is prompt caching.
                    # On first call: Claude computes + caches this block.
                    # On subsequent calls: reads from cache at ~10% cost.
                    "cache_control": {"type": "ephemeral"}
                }
            ],
            messages=[{"role": "user", "content": prompt}]
        )
        raw = message.content[0].text
        return raw

Prompt Caching — How It Saves 90% Cost

Prompt caching is one of the most impactful optimizations in your project. Here's exactly how it works:

  • First request: Claude processes _SYSTEM_PROMPT (the expert persona + JSON schema, ~500 tokens) and stores the computed key-value attention pairs in a cache. You pay full input token price + a small cache-write fee.
  • Subsequent requests (within 5 min): Claude reads from cache. You pay only ~10% of the original input token cost for those cached tokens.
  • Real savings: Your system prompt is ~500 tokens. At $3/million tokens (Claude Sonnet), that's $0.0015 per request. With caching: $0.00015 per request. 100 reviews/day saves $0.135/day = $49/year.
Token TypeCost (Sonnet)When charged
input_tokens$3/M tokensNew tokens not in cache (the PR diff)
cache_creation_input_tokens$3.75/M tokensFirst time you cache a block
cache_read_input_tokens$0.30/M tokensSubsequent reads from cache (10% price!)
output_tokens$15/M tokensClaude's JSON response
Minimum size for caching: 1,024 tokens for Claude Sonnet. Your system prompt must be at least that long to be eligible for caching.

📊 PyGithub + HMAC Webhooks

PyGithub is how your Code Review Agent reads PR diffs and posts comments. The webhook endpoint allows GitHub to automatically trigger reviews when PRs are opened or updated.

app/services/github_service.py — full walkthrough
import hashlib, hmac
from dataclasses import dataclass
from github import Github, GithubException

@dataclass
class PRDiff:
    """Aggregated PR data — DTO between GitHubService and the pipeline."""
    repo: str
    pr_number: int
    pr_title: str
    pr_url: str
    author: str
    base_branch: str
    head_branch: str
    files_changed: list[dict]   # [{filename, status, additions, deletions, patch}]
    diff_text: str               # full unified diff as a single string

class GitHubService:
    def __init__(self) -> None:
        settings = get_settings()
        # Github(token) authenticates all API calls
        # GitHub Personal Access Token needs 'repo' scope
        self._gh = Github(settings.github_token)
        self._max_diff_chars = settings.max_diff_chars  # 50,000 chars

    def fetch_pr_diff(self, repo_name: str, pr_number: int) -> PRDiff:
        repo = self._gh.get_repo(repo_name)   # returns Repository object
        pr = repo.get_pull(pr_number)          # returns PullRequest object

        files_changed = []
        diff_parts = []

        for f in pr.get_files():  # PaginatedList of File objects
            # f.filename = "src/auth.py"
            # f.status   = "modified" | "added" | "removed" | "renamed"
            # f.additions = lines added
            # f.deletions = lines removed
            # f.patch     = the actual diff patch (e.g., @@ -10,7 +10,9 @@ ...)
            files_changed.append({
                "filename": f.filename,
                "status": f.status,
                "additions": f.additions,
                "deletions": f.deletions,
                "patch": f.patch or "",
            })
            if f.patch:
                # Build unified diff format for the LLM prompt
                diff_parts.append(f"--- a/{f.filename}\n+++ b/{f.filename}\n{f.patch}")

        diff_text = "\n\n".join(diff_parts)
        # Truncate very large diffs to avoid hitting LLM context limits
        if len(diff_text) > self._max_diff_chars:
            diff_text = diff_text[:self._max_diff_chars] + "\n\n[... diff truncated ...]"

        return PRDiff(repo=repo_name, pr_number=pr_number, pr_title=pr.title,
                      pr_url=pr.html_url, author=pr.user.login,
                      base_branch=pr.base.ref, head_branch=pr.head.ref,
                      files_changed=files_changed, diff_text=diff_text)

    def post_review_comment(self, repo_name: str, pr_number: int, body: str) -> str:
        repo = self._gh.get_repo(repo_name)
        pr = repo.get_pull(pr_number)
        comment = pr.create_issue_comment(body)  # posts markdown as PR comment
        return comment.html_url

    @staticmethod
    def verify_webhook_signature(payload: bytes, signature: str) -> bool:
        """HMAC-SHA256 verification for GitHub webhook payloads."""
        secret = get_settings().github_webhook_secret
        if not secret:
            return True  # dev mode: skip verification

        # Compute expected signature
        expected = "sha256=" + hmac.new(
            secret.encode(),   # secret key as bytes
            payload,           # raw request body bytes
            hashlib.sha256     # algorithm
        ).hexdigest()

        # Use compare_digest to prevent timing attacks
        # (regular == is vulnerable to timing side-channels)
        return hmac.compare_digest(expected, signature)

HMAC Webhook Security — Why It Matters

When GitHub sends a webhook to your server, anyone on the internet could also send a fake POST to /webhook/github. HMAC verification proves the request genuinely came from GitHub:

  • You configure a secret in both GitHub's webhook settings and your .env
  • GitHub signs every webhook payload with HMAC-SHA256 using that secret and sends the signature in X-Hub-Signature-256 header
  • You recompute the signature on your end and compare
  • If they match, the request is genuine. If not, reject it (403).
Why hmac.compare_digest() instead of ==? Regular string comparison short-circuits at the first differing character, leaking timing information. An attacker could brute-force the signature bit by bit by measuring response times. compare_digest always takes the same time regardless of where strings differ.

📄 MongoDB + Motor — Async Database

Motor is the async MongoDB driver used in your Code Review Agent. Understanding it means you can explain async database operations and the MongoDB data model.

Why Motor Instead of PyMongo?

PyMongo is synchronous — it blocks the thread while waiting for MongoDB. In a FastAPI async app, blocking the event loop kills performance. Motor (Motor = async + PyMongo) provides the exact same API but all I/O operations return awaitables. Your async FastAPI handlers can await database calls without blocking.

OperationPyMongo (sync)Motor (async)
Insertcollection.insert_one(doc)await collection.insert_one(doc)
Find onecollection.find_one(filter)await collection.find_one(filter)
Find manycollection.find(filter).limit(n)await collection.find(filter).limit(n).to_list(n)
Updatecollection.update_one(f, update)await collection.update_one(f, update)

from pymongo import DESCENDING
from bson import ObjectId
from app.models.review import CodeReview

class DatabaseService:
    def __init__(self):
        settings = get_settings()
        # AsyncIOMotorClient creates a connection pool (not a single connection)
        client = AsyncIOMotorClient(settings.mongodb_uri)
        db = client["code_review_db"]       # database name
        self._col = db["reviews"]           # collection name

    async def save_review(self, review: CodeReview) -> str:
        # model_dump() converts Pydantic model to a plain dict
        doc = review.model_dump()
        result = await self._col.insert_one(doc)
        # insert_one returns InsertOneResult; .inserted_id is a BSON ObjectId
        return str(result.inserted_id)  # convert to string for API response

    async def get_review(self, review_id: str) -> dict | None:
        # ObjectId(review_id) converts string back to BSON ObjectId
        return await self._col.find_one({"_id": ObjectId(review_id)})

    async def list_reviews(
        self,
        repo: str | None = None,
        limit: int = 20,
        skip: int = 0
    ) -> list[dict]:
        filter_q = {}
        if repo:
            filter_q["repo"] = repo  # filter by repository name

        cursor = (
            self._col
            .find(filter_q)
            .sort("reviewed_at", DESCENDING)  # newest first
            .skip(skip)    # pagination: skip N documents
            .limit(limit)  # return at most N documents
        )
        # to_list(limit) fetches all results into a Python list
        return await cursor.to_list(limit)

    async def update_review_approval(
        self,
        review_id: str,
        approved_by: str,
        posted: bool = True
    ) -> None:
        await self._col.update_one(
            {"_id": ObjectId(review_id)},         # filter: find this document
            {"$set": {                              # $set: only update these fields
                "approved_by": approved_by,
                "posted_to_github": posted
            }}
        )

📈 TF-IDF + Cosine Similarity

Used in KeaBuilder AI (Demo 2) and KeaBuilder ML (Demo 1). TF-IDF is a classical NLP technique for finding similar text without any AI model. You must be able to explain the math and know when to use it vs sentence-transformers.

The Math — TF-IDF Explained Simply

TF (Term Frequency): How often does word W appear in document D, normalized by document length?

TF(w, d) = count(w in d) / total_words(d)

IDF (Inverse Document Frequency): How unique is word W across ALL documents? Rare words get higher scores; common words like “the” get penalized.

IDF(w) = log(N / df(w))    where N = total docs, df(w) = docs containing w

TF-IDF Score:

TF-IDF(w, d) = TF(w, d) × IDF(w)

Each document becomes a vector where each dimension = TF-IDF score of one word in the vocabulary. To find similarity, compute the cosine of the angle between two vectors.

cosine_similarity(A, B) = (A · B) / (|A| × |B|)    Range: 0 (no overlap) to 1 (identical)
demo2_similarity_search/app.py — your exact implementation explained
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity
import numpy as np

# Called on every request (no persistent state needed for small corpus)
def find_similar(query: str, corpus: list[dict], top_k: int):
    texts = [item["text"] for item in corpus]  # extract text strings
    all_texts = texts + [query]  # put query LAST

    vectorizer = TfidfVectorizer(
        ngram_range=(1, 2),   # include unigrams ("funnel") + bigrams ("sales funnel")
                              # bigrams capture phrases that change meaning together
        stop_words="english", # remove: the, is, a, for, ... (high IDF but no meaning)
        max_features=10000    # vocabulary cap: keep top 10,000 most informative terms
                              # prevents memory blow-up on large corpora
    )

    # fit_transform: (1) learns vocabulary from all_texts, (2) transforms all to vectors
    # Returns sparse matrix shape: (len(all_texts), vocabulary_size)
    # Sparse because most words appear in few documents (most entries are 0)
    tfidf_matrix = vectorizer.fit_transform(all_texts)

    # Extract the query vector (last row) and corpus matrix (all other rows)
    query_vector = tfidf_matrix[-1]          # shape: (1, vocab_size)
    corpus_matrix = tfidf_matrix[:-1]        # shape: (n_docs, vocab_size)

    # cosine_similarity returns matrix shape (1, n_docs)
    # [0] unwraps to 1-D array of scores
    scores = cosine_similarity(query_vector, corpus_matrix)[0]
    # scores[i] = similarity between query and corpus[i], range 0.0 to 1.0

    # Pair each score with its corpus item
    results = []
    for i, score in enumerate(scores):
        results.append({
            **corpus[i],
            "similarity_score": round(float(score), 4)
        })

    # Sort descending by similarity score
    results.sort(key=lambda x: x["similarity_score"], reverse=True)
    return results[:top_k]

Score Interpretation + Limitations

Score RangeMeaning
0.7 – 1.0Strong match — many shared keywords, similar phrasing
0.4 – 0.7Partial match — some shared terms
0.1 – 0.4Weak match — few shared words
0.0 – 0.1No meaningful overlap

Why TF-IDF fails on semantics: “I want to sell my coaching program” and “monetize my mentoring service” share zero keywords, so TF-IDF gives them a score near 0. But they mean the same thing. This is the limitation that sentence-transformers solves by encoding meaning into dense vectors.
