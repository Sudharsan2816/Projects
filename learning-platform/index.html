Design Patterns Used

  • Factory Pattern — _build_llm_client() returns either ClaudeClient or OpenAIClient based on env config. You never hardcode the provider.
  • Abstract Base Class — BaseLLMClient(ABC) defines the interface. Both Claude and OpenAI must implement generate_review() and parse_review_response().
  • State Machine — LangGraph StateGraph ensures each step only executes if no error occurred in previous steps.
  • Repository Pattern — DatabaseService wraps all MongoDB calls. The rest of the app never touches raw Motor/pymongo.
  • DTO (Data Transfer Object) — PRDiff dataclass carries all GitHub data cleanly between services.
💡 Key insight: The LangGraph agent and ReviewService both implement the same pipeline. LangGraph makes it composable — you can add a "security scanner" node without touching the existing code.

FastAPI — The Modern Python Web Framework

FastAPI is the foundation of every project you built. Understanding it deeply means you can explain exactly how your APIs work, why they are fast, and how they auto-generate documentation.

📚

What is FastAPI? (And why not Flask/Django?)

FastAPI is an ASGI (Asynchronous Server Gateway Interface) web framework. ASGI is the modern successor to WSGI. The key difference:

FeatureWSGI (Flask, Django)ASGI (FastAPI)
Concurrency modelOne request at a time per workerThousands of concurrent requests, single thread
async/awaitNot native (workarounds exist)First-class citizen
Type hintsOptional, no integrationCore feature — drives validation + docs
Auto-docsManual or with extensionsBuilt-in /docs (Swagger) + /redoc
Performance~1000-3000 req/s~30,000+ req/s (matches Node.js)

FastAPI is built on Starlette (the ASGI toolkit) and Pydantic (data validation). When you declare a route with type hints, FastAPI automatically validates incoming data and serializes outgoing data.

🧠 Mental Model

Think of WSGI like a bank with one teller per queue. Each customer waits in line. ASGI is like a bank with a digital queuing system — the teller can call the next customer while the previous one is waiting for their form to be processed (I/O wait). FastAPI is that modern bank.

🔑

FastAPI App Creation (from your projects)

Every FastAPI app starts the same way. Here's how you did it in your lead classifier:

demo1_lead_classifier/app.py — App creation + middleware
from fastapi import FastAPI, HTTPException
from fastapi.middleware.cors import CORSMiddleware

# FastAPI instance with metadata (feeds the auto-docs at /docs)
app = FastAPI(
    title="KeaBuilder Lead Classifier",
    description="AI-powered lead qualification using Claude.",
    version="1.1.0",
    docs_url="/docs",    # Swagger UI
    redoc_url="/redoc"   # ReDoc UI
)

# CORSMiddleware allows browser JS to call this API from any domain.
# In production, replace ["*"] with your actual frontend domain.
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],   # Which origins can call this API
    allow_methods=["*"],   # GET, POST, PUT, DELETE, etc.
    allow_headers=["*"],   # Authorization, Content-Type, etc.
)

Route Decorators — The Core of FastAPI

Route decorators map HTTP methods + paths to Python functions. FastAPI reads your type annotations to know what to expect.

Route patterns used in your projects
# --- Pattern 1: Simple GET (no body, no path param) ---
@app.get("/health", response_model=HealthResponse, tags=["Health"])
def health():  # sync is fine for instant returns
    return HealthResponse(status="ok", service="lead-classifier")

# --- Pattern 2: GET with path parameter ---
@app.get("/review/{review_id}")
async def get_review(review_id: str):  # {review_id} maps to the arg
    doc = await db.get_review(review_id)
    if not doc:
        raise HTTPException(status_code=404, detail="Review not found")
    return doc

# --- Pattern 3: GET with query parameters ---
@app.get("/review")
async def list_reviews(
    repo: str | None = None,   # optional: /review?repo=owner/repo
    limit: int = 20,            # /review?limit=10
    skip: int = 0               # /review?skip=20 (pagination)
):
    return await review_svc.list_reviews(repo=repo, limit=limit, skip=skip)

# --- Pattern 4: POST with request body (most common) ---
@app.post("/classify-lead", response_model=LeadOutput, tags=["Lead Classification"])
async def classify_lead(lead: LeadInput):  # LeadInput is a Pydantic model
    # FastAPI auto-parses + validates the JSON body into `lead`
    # If validation fails, it returns 422 Unprocessable Entity automatically
    if not lead.message or len(lead.message.strip()) == 0:
        raise HTTPException(status_code=400, detail="Message cannot be empty")
    # ... process ...

# --- Pattern 5: POST with response model (code_review_agent) ---
@app.post("/review", response_model=ReviewResponse)
async def trigger_review(body: ReviewRequest):
    # body.repo_name, body.pr_number, body.post_comment
    review, review_id = await review_svc.run_review(
        body.repo_name, body.pr_number, body.post_comment
    )
    return ReviewResponse(review_id=review_id, review=review)

async def vs def — When to Use Each

This is one of the most important decisions in FastAPI. The rule is simple:

  • Use async def when your function does I/O: calls an API, reads from DB, reads a file. This lets FastAPI serve other requests while waiting.
  • Use regular def when your function is CPU-bound or instant. FastAPI runs it in a thread pool automatically to avoid blocking the event loop.
In your code: classify_lead is async def because it awaits the Anthropic API. health() is regular def because it just returns a dict instantly.
HTTPException — how to return errors properly
from fastapi import HTTPException

# Raising HTTPException stops execution and returns an HTTP error response
raise HTTPException(
    status_code=400,          # HTTP status code
    detail="Message too short" # goes into JSON response body: {"detail": "..."}
)

# Common status codes you use:
# 400 Bad Request   - invalid input from client
# 401 Unauthorized  - no/bad token
# 403 Forbidden     - token valid but no permission
# 404 Not Found     - resource doesn't exist
# 422 Unprocessable - Pydantic validation failed (FastAPI auto-raises this)
# 500 Server Error  - something broke on your side
# 502 Bad Gateway   - upstream API (Anthropic, GitHub) failed

Pydantic v2 — Data Validation & Settings

Pydantic is the data layer of every FastAPI project. It validates inputs, serializes outputs, and loads environment variables. Understanding it means you can design airtight APIs.

📚

BaseModel — The Foundation

Every Pydantic model inherits from BaseModel. When you instantiate it, Pydantic automatically validates all fields against their type annotations. If a field is wrong, it raises ValidationError.

app/models/review.py — your actual Pydantic models
from datetime import datetime
from enum import Enum
from typing import Optional
from pydantic import BaseModel, Field

# --- Enum with str mixin ---
# str Enum means: the value IS the string, so JSON serialize works cleanly
class Verdict(str, Enum):
    APPROVE = "APPROVE"
    REQUEST_CHANGES = "REQUEST_CHANGES"
    COMMENT = "COMMENT"

# --- Nested model with Field constraints ---
class Scores(BaseModel):
    quality: int = Field(..., ge=1, le=10)    # ... = required, ge=min, le=max
    security: int = Field(..., ge=1, le=10)
    performance: int = Field(..., ge=1, le=10)

# --- Optional fields ---
class FindingItem(BaseModel):
    file: Optional[str] = None          # None = optional, defaults to None
    line: Optional[int] = None
    description: str                     # required, no default
    severity: Optional[str] = None

# --- Complex model with defaults ---
class CodeReview(BaseModel):
    repo: str
    pr_number: int
    pr_title: str
    pr_url: str
    reviewed_at: datetime = Field(default_factory=datetime.utcnow)  # callable default
    llm_provider: str

    # default_factory=list: each instance gets its OWN empty list
    # (never use [] as default directly in Pydantic v2 — use default_factory)
    bugs: list[FindingItem] = Field(default_factory=list)
    security: list[FindingItem] = Field(default_factory=list)
    performance: list[FindingItem] = Field(default_factory=list)
    code_quality: list[FindingItem] = Field(default_factory=list)
    suggested_fixes: list[SuggestedFix] = Field(default_factory=list)

    scores: Scores                       # nested model — Pydantic validates recursively
    final_verdict: Verdict               # must be one of the Verdict enum values
    summary: str
    posted_to_github: bool = False
    approved_by: Optional[str] = None

BaseSettings — Loading Environment Variables

Your app/config.py uses BaseSettings from pydantic-settings. It automatically reads environment variables (and .env files) and validates them just like a regular Pydantic model.

app/config.py — Settings pattern from code_review_agent
from pydantic_settings import BaseSettings, SettingsConfigDict
from functools import lru_cache

class Settings(BaseSettings):
    # These field names map DIRECTLY to env var names (case-insensitive)
    github_token: str                          # requires GITHUB_TOKEN env var
    anthropic_api_key: str = ""               # optional with default
    openai_api_key: str = ""
    llm_provider: str = "claude"               # default to claude
    mongodb_uri: str = "mongodb://localhost:27017"
    claude_model: str = "claude-sonnet-4-6"
    max_diff_chars: int = 50_000
    require_human_approval: bool = False
    github_webhook_secret: str = ""

    model_config = SettingsConfigDict(
        env_file=".env",      # also read from .env file
        case_sensitive=False  # GITHUB_TOKEN = github_token
    )

# lru_cache makes get_settings() return the SAME Settings instance
# every time (singleton pattern) instead of re-reading env vars each call
@lru_cache
def get_settings() -> Settings:
    return Settings()

# Usage anywhere in the codebase:
# from app.config import get_settings
# settings = get_settings()
# token = settings.github_token
🧠 Mental Model

Think of BaseSettings as a smart configuration reader. It checks environment variables first, then falls back to the .env file, then uses defaults. The lru_cache ensures you parse the env only once at startup, not on every API call. It's like reading a config file once when the server starts and caching it in memory.
